# Implementation decisions

1. The supplied repository was empty. The build preserves the requested FastAPI, aiosqlite, raw Telegram API and vanilla ES module stack. Git commits use the specified author and committer.
2. The owner confirmed that Vultr and Telegram accounts/bot do not exist yet. No paid resource, bot token, public deployment or submission is invented. Deployment instructions and submission material are prepared instead.
3. Real intake always requires coordinator authentication for state-changing API actions, even in demo mode. Open approvals apply only to simulated pairs. Simulation is permanently isolated from Telegram notification delivery.
4. Remote geocoding is disabled by default. The operator must deliberately set a service URL and identifying contact User-Agent. Cached requests are serialized at no more than one per second. Only broad locality queries should be sent. This supports the current OSM privacy and usage policies.
5. The default local gazetteer contains approximate locality centres, not street-level addresses. It is enough for the fictional drill; unknown locations are not invented.
6. Development can start without secrets. A random per-process salt is used if none is supplied; a stable SALT is mandatory for repeat Telegram use and required in production. Production enforces secret lengths. The deployment script generates independent secrets without printing them.
7. Hashes group senders; separate private routing IDs are retained solely to send approved Telegram mentions. Public routes never expose those IDs. `/forget` deletes the routing records too.
8. The fallback supports a limited explicit vocabulary. It retains original text as the English-summary field; the UI calls this an English summary, and README discloses that fallback does not translate. It never pretends to be equivalent to provider extraction.
9. Fallback rules and fixtures are synthetic template checks. Gold labels are declared independently in `scripts/build_data.py`; results are calculated by actually executing extraction. This is not an independent held-out or real-world benchmark.
10. Canonical items must be ≥0.8 similar in addition to the requested weighted threshold. This prevents a near-by but clinically different item from matching merely through distance/urgency.
11. One offer card is reserved as a whole on approval. Quantities are displayed but partial allocation is outside this prototype. Conflicting suggestions are rejected atomically.
12. Message text is capped at 1000 characters and request bodies at 16 KiB, including chunked writes. Raw text is never logged. Trusted acknowledgement templates avoid echoing contact information or provider-produced instructions into group replies.
13. Per-chat bot messages are serialized at least two seconds apart. Unsupported media warnings are limited to once per hour per chat. Commands and pin handling are supported; voice/call handling is not.
14. The full long-poll update offset is stored in SQLite after durable intake. Edited messages update their existing card; source changes invalidate suggestions and approved allocations. Post-approval edits need human review again.
15. Card ordering is computed globally in SQL before offset pagination. Under changing live data, pages are best effort and refresh from the first page. Match lists use stable ascending ID cursors.
16. UI app modules are under the requested size target. Leaflet 1.9.4 is vendored from its npm release with its license. Fontsource 5.3.0 supplies self-hosted Inter variable Latin, Noto Sans Tamil Tamil and JetBrains Mono Latin WOFF2 files with licenses. Only glyph subsets needed by this prototype are included.
17. Shared UI dictionaries cover English, Tamil, Spanish and German. Informational prose and some operational metadata remain English. Independent native Tamil review is pending; `docs/TAMIL_REVIEW.md` is the checklist. No language certification is claimed.
18. Mobile uses fixed bottom tabs and a bottom-sheet drawer. Tablet uses map-first layout with two panels; desktop uses three columns. Automated overflow and JavaScript checks are recorded separately from any accessibility certification.
19. Docker Compose uses a named runtime volume, a non-root/read-only app container and Caddy. The image uses Python 3.12; local tests use installed Python 3.11. Docker and an Ubuntu server were unavailable, so target-host execution remains pending. CI tests Linux/Python 3.12.
20. The setup script installs Docker from its official apt repository; it never pipes a downloaded installer into a shell. Existing `.env` and data are preserved. Updates are an explicit `git pull --ff-only` and rebuild.
21. HTTP-by-IP is supplied for initial simulated testing; HTTPS should precede real coordinator login/intake. Proxy trust is safe only while port 8000 stays loopback-only and Caddy is the public entry point.
22. Phone/email/street redaction is heuristic and cannot recognise every address format. Do not enter confidential data. Public coordinates are approximate, not a formal anonymity guarantee.
23. Submission text uses only supplied evidence, with links. Some source pages could not be fetched by the verification browser; their claims remain attributed to the owner-supplied source list. No extra disaster statistics are introduced.
24. Screenshots and a silent local walkthrough demonstrate actual simulated UI interaction. They do not prove public deployment, live transport or human adoption. Record the final live Telegram clip after account setup.
25. No artificial commit splitting, fabricated dates, fake usage metrics or claimed native review is used. Every verification report describes its actual scope.
